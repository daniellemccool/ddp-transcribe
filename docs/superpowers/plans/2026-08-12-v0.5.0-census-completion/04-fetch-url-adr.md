Content to carry (adapt to the lean format):

- **Title (imperative digest):** "Derive the fetch URL, never rewrite provenance"
- **Scope / applies_to:** `src/pipeline/mod.rs`, `src/canonical.rs`, `src/backfill.rs`, `src/state/mod.rs`, `src/output/artifacts.rs`
- **Decision:** For `canonical = 1` claims, the URL handed to yt-dlp is
  derived from the primary key at fetch time —
  `https://www.tiktok.com/@x/video/<video_id>/` — via one helper
  (`canonical::derived_fetch_url`). `videos.source_url` is immutable DDP
  provenance: never rewritten in bulk, never mutated by transport
  concerns, and it is what transcript artifacts carry (ADR-0010/0042
  posture). Transport form is code + `params_json`, not data.
- **Why (evidence):** the 2026-08-06 and 2026-08-10 WAF incidents blocked
  the stored share-host URL form (`www.tiktokv.com/share/video/…`) at the
  first hop; the canonical form fetches unimpersonated (probe matrix in
  the incident-2 record). The alternative — a 1.93M-row `UPDATE` of
  `source_url` (incident-2 "remaining steps") — mutates researcher-visible
  provenance and is superseded by this decision; that SQL must never run.
- **Guidance:**
  - The `@x` placeholder is deliberate: `CANONICAL_RE`
    (`src/canonical.rs:23-28`) requires a non-empty user segment
    (`@[^/]+`), and an empty `@` URL would classify `Invalid` if it ever
    re-entered canonicalization. Any non-empty segment fetches
    identically (verified 2026-08-11).
  - Non-canonical rows (`canonical = 0`, Plan C short-links) keep fetching
    their stored `source_url`; review rejects derivation widening to them
    without their own evidence.
  - Every production yt-dlp URL consumer uses the same helper — pipeline
    fetch AND `backfill-metadata`; review rejects a second URL-format
    string literal.
  - Cookie scoping (0035) and format policy (0038) read the claim, not
    the URL — derivation must not alter either decision point.
